# Windows installer payload

From `apps/desktop-tauri`, run `sh packaging/windows/xbuild.sh package` with the existing cross-build image. Host Node stages the runtime before the container build; Node is not required in the image. This command does not install or launch Abito. Follow-up (K2-02): `xbuild.sh` does not yet build the bundled Node+Pi runtime archive (`packaging/runtime/build-runtime.cjs --target win-x64 --archive`) nor write `abito-install.json`; until it does, the cross-built installer is not a shippable K2-02 installer. The native CI path (`preview-windows.yml`) is the supported build.

`node packaging/windows/stage-runtime.cjs [--out DIRECTORY] [--runtime-archive FILE]` copies exactly `DAEMON_FILES`, `HARNESS_FILES` and `PI_FILES` exported by `packaging/lib.cjs`, defaulting to gitignored `dist/windows-runtime`. It generates `runtime.nsh` from those same lists. Existing unknown entries and symlinks are rejected rather than removed. Staging without `--runtime-archive` into an output directory that still holds a `koda-runtime.tar.gz` from an earlier run is refused: the stale `koda-runtime.tar.gz` is never reused silently (exit 1, nothing removed or rewritten); stage with `--runtime-archive` to replace it, or remove it yourself. With `--runtime-archive` (K2-02 T2, decision B) it also stages the bundled Node+Pi runtime archive (from `packaging/runtime/build-runtime.cjs --archive`) as `koda-runtime.tar.gz` and embeds its stage-time sha256 in `runtime.nsh` as `KODA_RUNTIME_SHA256`. `--help` describes the CLI.

The installer contains these sibling executables:

- `abito-island.exe`
- `abito-notice-relay.exe`
- `abito-private-session.exe`

`abito-private-session --verify` performs a read-only native status check using the same canonical root as publication: strict session-file ACL/owner, live daemon PID, pipe server PID/SID, then authenticated hello→ready. It accepts no path argument, never prints a token, writes nothing, and returns only a silent exit code (0 verified, 1 refused). `--help` describes both modes. Windows daemon CLI `status` uses this fixed sibling helper instead of a Node-only pipe probe; failure or a missing helper is not healthy. This does not authorize `stop` to signal a bare Windows PID.

The closed `desktop-daemon`, `desktop-harness` and `desktop-pi` directories live beside them. Shipping the Pi payload does not enable automatic extension installation on Windows; that remains explicitly unavailable. Koda no longer needs an external Node or Pi: the installer ships its own pinned runtime (K2-02) as ONE tar.gz whose sha256 is embedded in `runtime.nsh` at makensis time. `abito.nsi` fails the BUILD (`!error "K2-02: the runtime archive was not staged (stage-runtime.cjs --runtime-archive)"`) when `runtime.nsh` carries no `KODA_RUNTIME_SHA256`, i.e. when no archive was staged: a shipped Koda must carry its runtime, so an installer without it is never built silently.

Install order in `Section "Koda"` (slice10):

1. `AbitoVerifyRuntime`: NSIS `File`s the archive into `$INSTDIR` and verifies it with `certutil -hashfile ... SHA256` (case-insensitive, spaces normalised) before the payload is written. A bad archive deletes itself and aborts with nothing changed.
2. `AbitoInstallPayload`: the closed per-file payload.
3. `WriteUninstaller`: written before the runtime swap, so an install that fails during extraction is still removable with `uninstall.exe`.
4. `AbitoInstallRuntime`: extracts with `$SYSDIR\tar.exe` into a fresh `$INSTDIR\runtime.new`, renames the live `$INSTDIR\runtime` aside to `$INSTDIR\runtime.old`, renames `runtime.new` to `runtime`, then removes `runtime.old` (guarded) and the archive. If the activation fails the previous runtime is renamed back from `runtime.old` and the install aborts; a failed move-aside leaves the current runtime untouched. The old runtime is never deleted before the new one is in place.

If step 4 fails the payload and `uninstall.exe` remain (no Start-menu or Add/Remove entry yet): on a fresh install there is no runtime, on an upgrade the previous runtime is kept or restored. The archive and `runtime.new` are removed before aborting; the uninstaller also removes any leftover `runtime`, `runtime.old`, `runtime.new` and archive.

Recursive removal is guarded (`AbitoRuntimeGuardedRmDirR`, the only `RMDir /r`): it refuses an empty target or a drive root (`StrLen <= 3` on the target itself), an empty `$INSTDIR` or a drive root, a target that is not strictly under `$INSTDIR\` (so neither `$INSTDIR` itself nor a sibling such as `$INSTDIR-x`), and a reparse point or junction (`GetFileAttributesW` `FILE_ATTRIBUTE_REPARSE_POINT`). The archive path is always passed quoted to `certutil` and `tar`.

Known limit (R1-001): there is a TOCTOU window between the reparse-point attribute check and `RMDir /r`. It is accepted, not fixed: the install is per-user (`RequestExecutionLevel user`, `$LOCALAPPDATA\Programs`, no directory page), so exploiting it needs another process with same-user write access to `$INSTDIR`, and such a writer already controls everything Koda runs. A missing target (`GetFileAttributesW` returns -1) is harmless.

For native Windows packaging, stage with Node, copy the three built executables to `dist`, and invoke NSIS with `VERSION`, `BINDIR`, `ICON`, and `OUTDIR`. `RUNTIMEDIR` defaults to `${BINDIR}\windows-runtime`; the native workflow passes it explicitly. NSIS source paths, including the generated `File` entries, use backslashes. The generated include is BOM-free ASCII with LF line endings and drives both native and cross packaging. Before native compilation, CI prints the runtime directory argument, staged file list, and include header to distinguish missing payloads from NSIS path resolution failures.

Windows daemon and receiver directories share one privacy policy: the owner is the current user or BUILTIN\\Administrators, and every understood ACL principal is the current user, SYSTEM or BUILTIN\\Administrators. NULL DACLs, other principals, unknown ACE types and reparse-point paths are refused. Rust creates missing directories with a protected user+SYSTEM DACL and explicit current-user ownership at creation; it never rewrites an existing directory ACL. Existing profile ancestors outside the canonical Abito directory need to be real directories, not match Abito's private ACL. Endpoint metadata and daemon session files retain their stricter current-user-only policy.

Uninstall deletes only listed payload files and `uninstall.exe`, then removes empty owned directories deepest first. It does not recursively delete directories or remove unrelated files or island user configuration — the one exception is the bundled runtime directory, removed with the guarded recursive removal described above. The per-user shortcut and uninstall registry entry are removed.

After packaging, `node packaging/windows/stage-win.cjs` records hashes for all three executables, the setup executable, staged runtime and generated include, plus packaging/runtime/frontend source inputs. `node packaging/windows/stage-win.cjs --check` checks the exact receipt sets and hashes against the current artifacts and inputs, and rejects stale runtime copies. The staged archive's bytes are pinned transitively through `runtime.nsh` (its `KODA_RUNTIME_SHA256`), and `abito-install.json` pins `runtime/node.exe` when `install-manifest.cjs` runs with `--runtime <build-runtime out>`. This is provenance checking, **not** proof that Windows installation or runtime launch works; the native CI install smoke supplies that evidence.

Local contract test: `node test-node/windows-runtime-check.cjs`. It stages an isolated payload, checks require closure and install/delete equivalence, exercises preservation of unrelated files, and runs the receipt CLI with tampered artifacts and inputs.

## Native preview smoke

`ci/public/preview-windows.yml` refuses non-GitHub-hosted runners before checkout or tool setup. It parses both PowerShell scripts before any account operation, executes native policy/receiver/daemon and real foreign-user tests, builds the release installer, then invokes `ci/public/smoke-windows.ps1 -Setup <setup.exe>`. NSIS is reused from the runner when available; only a disposable hosted runner may use the pinned 3.11 Chocolatey fallback.

The smoke installs silently in a fresh runner-temp directory and compares every installed payload file to the staged payload. The main launch leaves `ABITO_PROJECT_ROOT` absent to exercise the installed `USERPROFILE` fallback; a second launch supplies a normalized absolute Windows root. Explicit roots accept drive-absolute and UNC paths, rejecting relative paths, dot segments, empty segments and invalid/trailing Windows filename characters. Failures print bounded island/daemon stderr and directory ACL metadata, never session/token/config contents. It installs real Pi into an isolated npm prefix, starts the installed island, checks authenticated installed daemon status, and sends a Claude Stop event through the installed hook and native relay. Success requires the island to log exactly one content-free `island: settled notice accepted` line, not merely hook process success. A broken-runtime launch (the installed `runtime\koda-runtime.json` moved away) must print `island host: no_daemon (bundled_runtime_invalid)` and the reinstall sentence without starting the daemon. Uninstall must remove every shipped file while preserving an unrelated fixture and island user data (WebView2's own `EBWebView` cache, which a lingering browser process keeps locked, is not hashed). Logs are uploaded even on failure; no recursive profile cleanup runs. A second script, `ci/public/smoke-windows-runtime.ps1`, installs the same setup into its own runner-temp directory and proves the bundled runtime itself: `runtime\node.exe --version` matches the pin in `packaging/runtime/node.sha256`, the bundled Pi answers `--version` with the pin from `packaging/runtime/package.json` offline (`PI_OFFLINE=1`, `PI_SKIP_VERSION_CHECK=1`, `PI_TELEMETRY=0`, private empty `HOME`/`USERPROFILE`/`APPDATA`), `koda-runtime.tar.gz` is not left in `$INSTDIR`, and after uninstall `$INSTDIR\runtime` is gone.

`node test-node/windows-ci-check.cjs` checks guard placement structurally. It does not replace native PowerShell parsing or the full Windows smoke.

K2-13 T2c-2: `abito-transcribe.exe` (the Minikodas' sherpa-onnx transcription helper) is one of the `BINARY_FILES` installed and deleted beside `abito-island.exe`. The pinned LGPL `ffmpeg.exe` travels inside the runtime archive (`runtime\ffmpeg.exe` + `runtime\LICENSE.ffmpeg.txt`, built by `build-runtime.cjs --target win-x64`), so it is removed with the guarded runtime directory. `install-manifest.cjs --runtime` pins it as `runtime/ffmpeg.exe`. The native CI build (`preview-windows.yml`) must copy `target/release/abito-transcribe.exe` into `dist/` with the other helpers.
